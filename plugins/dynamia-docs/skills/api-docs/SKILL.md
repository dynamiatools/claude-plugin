# dynamia-docs:api-docs

## Doc comments (what to write)
A doc comment states the **contract**: what the element does, what it expects, what it returns or throws, side effects, thread-safety, units, null/empty behavior, and since when. It does not narrate the implementation and it does not restate the name (`/** Gets the name. */` adds nothing).

| Language | Syntax | Notes |
|---|---|---|
| **Java** | `/** ... */` with `@param`, `@return`, `@throws`, `@see`, `@since`, `@deprecated` (plus the `@Deprecated` annotation); `{@code x}`, `{@link Type#member}`; `{@snippet}` for checked examples (JDK 18+); Markdown doc comments with `///` since JDK 23 | first sentence is the summary (shown in indexes); document every public/protected element of a library API |
| **Kotlin** | KDoc `/** ... */` with Markdown; `@param`, `@return`, `@property`, `@constructor`, `@receiver`, `@throws` (optional: no checked exceptions), `@sample`, `@see`, `@since`, `@suppress`; links `[Name]` and `[label][Name]`, qualified names with dots | **no `@deprecated` tag**: use the `@Deprecated` annotation; generated by **Dokka**; the first paragraph is the summary |
| **TypeScript** | TSDoc `/** ... */` with `@param`, `@returns`, `@remarks`, `@example`, `@deprecated` | document exported APIs; types already say the shapes, comments say behavior and constraints |

Rules:
1. **Summary first** (one sentence, third person, ends with a period); details after a blank line.
2. Document **behavior at the edges**: null, empty, negative, overflow, concurrency, ordering, idempotency, exceptions and when they happen, units and time zones.
3. **Examples** that compile and are tested (`{@snippet}`, `@sample`, `@example`, or doctests/tests); an example beats a paragraph.
4. Say **why** when it is not obvious (a constraint, a workaround, a link to the ADR/issue).
5. Deprecation says what to use instead and when it will go (`dynamia-docs:changelog`).
6. Keep comments true: when code changes, change the comment in the same commit; delete comments that only restate code.
7. Don't document private details in public docs; don't paste secrets or internal hostnames.

## OpenAPI (REST APIs)
Latest specification read on 2026-10-23: **OpenAPI 3.2.1** (10 September 2026); parsing follows JSON Schema Draft 2020-12. Structure: `info` (title, version, description, contact, license), `servers`, `paths` (operations), `components` (reusable schemas, parameters, responses, security schemes), `security` (global requirements, overridable per operation), `webhooks`. Check which version your toolchain supports (generators and Spring/Ktor libraries lag the spec) before choosing 3.0, 3.1 or 3.2.
- Every operation: `operationId` (stable, unique), `summary` and `description`, tags, all parameters with schema/description/examples, request body with examples, **every response status** (2xx and the errors the API really returns) with schema, and its security requirement.
- Schemas in `components`, referenced with `$ref`; constraints (`required`, `format`, `minimum`, `maxLength`, `enum`) match the validation code; examples are realistic and valid against the schema.
- Errors use one consistent shape (for example RFC 9457 problem details).
- **Generate or hand-write, but keep one source of truth**: code-first (annotations / library output) with the spec published from CI, or spec-first with generated server stubs/clients. Never let the doc and the code be edited separately.
- **Validate** the file with a linter in CI and **test the contract** (requests/responses against the schema) so the doc cannot drift.
- Versioning: the API version in `info.version` follows the API's own policy (`dynamia-docs:changelog`); breaking changes are announced.

## Reference docs generation
Javadoc (`maven-javadoc-plugin`), Dokka for Kotlin, TypeDoc/API Extractor for TypeScript: build them in CI, fail on broken links and missing documentation of the public API if the project decides so, publish with the release.

## Review checklist
- [ ] Public API fully documented; summaries meaningful; edge behavior stated.
- [ ] Examples compile/run; links resolve; deprecations explain the replacement.
- [ ] OpenAPI: every operation has operationId, responses (incl. errors), examples and security; schemas match the code.
- [ ] No comment contradicts the code.

End with one line: what was documented or fixed, what was validated (build, linter), what was not.
